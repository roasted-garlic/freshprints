---

## Goal

Investigate and design a reduction in catalog image Storage usage — evaluating whether the
separate `/thumbnails/{designId}.webp` (320×320) and `/previews/{designId}.webp` (1280×1280)
objects can be replaced by one shared optimized WebP display derivative — while preserving the
original production PNG, print quality, transparency, Portal/Studio performance, and a
non-destructive, staged, rollback-safe migration. **This phase produces a Plan and Formal Review
only. No implementation, migration, backfill, deletion, or deployment occurs.**

---

## Background / Owner Concern

Storage usage appeared high relative to only ~80 catalog designs. The architecture creates up to
three Storage objects per design (`/originals/{id}.png`, `/thumbnails/{id}.webp`,
`/previews/{id}.webp`), plus temporary duplication during customer-upload promotion. The owner
asked whether a single shared WebP display derivative could replace both preview and thumbnail.

## Investigation Findings (from repository evidence, cited exactly)

### 1. Object families and exact Storage paths

Deterministic path helpers — `packages/shared/src/constants/design/designStoragePaths.ts:12-22`:

```
getOriginalStoragePath(designId)  -> /originals/{designId}.png
getThumbnailStoragePath(designId) -> /thumbnails/{designId}.webp
getPreviewStoragePath(designId)   -> /previews/{designId}.webp
```

Content-addressed by `designId` only — **overwrite-in-place**, no content-hash/version segment in
the path itself. Confirmed identical in `storage.rules:72-105` (`isCanonicalOriginalFileName` /
`isCanonicalDerivativeFileName` regexes match exactly these three prefixes/extensions).

Every catalog design normally has all three objects. Additional families:

- `/generated/catalog-reference/**` — server-private + public taxonomy/reference JSON
  (`storage.rules:230-242`; ADR-FP-120). References design **paths**, not bytes.
- `/generated/portal-catalog/**` — public Portal catalog manifest/card-bucket JSON
  (`storage.rules:244-247`; ADR-FP-120). Same — paths, not embedded bytes.
- `/customer-uploads/{uid}/{uploadId}/{source|production|preview|thumbnail}` — a **separate**
  object family (ADR-FP-073, Goal #11 territory) that becomes catalog-adjacent only during
  promotion (see §5). Out of scope to modify directly, in scope to understand as a duplication
  source.

### 2. Estimated object/byte cost per design

- Original: PNG, ≤150 MB per Storage Rules cap (`storage.rules:63`), typically much smaller in
  practice for real catalog art — exact average size **[NEEDS MEASUREMENT — see §Storage
  Measurement Method below; not knowable from source alone]**.
- Preview: WebP, max 1280×1280 bounding box, quality 85, alpha-preserving, downscale-only
  (`derivativeGeneration.constants.ts`).
- Thumbnail: WebP, max 320×320 bounding box, quality 80, alpha-preserving, downscale-only (same
  file).
- Both derivatives capped at 10 MB by Storage Rules (`MAX_DERIVATIVE_FILE_SIZE_BYTES`,
  `storage.rules:68-70`) but real WebP output at these dimensions/quality is expected to be one to
  two orders of magnitude smaller than that ceiling — **not measured from source; requires the
  inventory tool below**.
- **Per-design object count today: 3 permanent (original + preview + thumbnail), briefly up to 6
  during a promotion-in-flight window** (customer-upload's own source/production/preview/thumbnail
  plus the newly-copied catalog original/preview/thumbnail, until the 14-day cool-off purge —
  ADR-FP-086 §4).

### 3. Preview/thumbnail dimensions, format, quality — confirmed identical generation logic in two places

`packages/shared/src/constants/import/derivativeGeneration.constants.ts` (single source of truth,
imported by both):

| Constant | Value |
|---|---|
| `THUMBNAIL_MAX_WIDTH_PX` / `THUMBNAIL_MAX_HEIGHT_PX` | 320 / 320 |
| `THUMBNAIL_WEBP_QUALITY` | 80 |
| `PREVIEW_MAX_WIDTH_PX` / `PREVIEW_MAX_HEIGHT_PX` | 1280 / 1280 |
| `PREVIEW_WEBP_QUALITY` | 85 |
| `DERIVATIVE_WEBP_CONTENT_TYPE` | `image/webp` |
| `DERIVATIVE_ALLOW_UPSCALE` | `false` |
| `DERIVATIVE_PRESERVE_ALPHA` | `true` |
| `MAX_DERIVATIVE_FILE_SIZE_BYTES` | 10 MiB (Storage Rules ceiling) |

Generated **independently in parallel from the same source bytes**, not chained
(`derivativeGenerationService.ts:56-96` in Studio Electron; `customerUploadProcessing.ts:606-623`
in Functions — both call `sharp(...).resize(maxW, maxH, { fit: "inside", withoutEnlargement: true
}).webp({ quality, alphaQuality: quality })`, confirmed via `encodeWebpDerivative.ts:61-79`).
Dimensions/quality/format are **identical whether generated by Studio import (Electron sharp) or
by Functions (server sharp, customer-upload/donation path)** — one shared constants file, no
divergence to reconcile.

**No `Cache-Control` metadata is set on any of the three catalog object families** — confirmed by
repo-wide grep; contrast with customer-upload objects (`cacheControl: "private, max-age=3600"`,
`customerUploadProcessing.ts:975-994`) and generated JSON (`publishCatalogSnapshots.ts:105-129`),
both of which do set it. This is a pre-existing gap, not introduced by this Plan, but directly
relevant to Required Technical Analysis item 11 below.

**`originalPath`**, **`thumbnailPath`**, **`previewPath`** (optional), **`width`/`height`**
(source PNG pixel dimensions, not derivative dimensions —
`design.types.ts:17-28`). No `thumbnailUrl`/`previewUrl`/`originalUrl` fields exist; every consumer
resolves a Storage **path** to a download URL client-side.

**Pattern found across every consumer, with zero exceptions:**

**Conclusion from evidence:** every grid surface already only reads `thumbnailPath`; every detail
surface already prefers `previewPath` but gracefully falls back to `thumbnailPath` when absent.
This existing fallback behavior is the single most important structural fact for this Plan — it
means **a missing `previewPath` is already a supported, non-breaking state** in every consumer
found. That materially de-risks a staged migration (see Migration Design below).

### 5. Customer-upload promotion into the catalog

`functions/src/promoteCustomerUploadToAiReview.ts` **copies** bytes
(`bucket.file(productionStoragePath).copy(bucket.file(originalPath))`, lines 38-63), it does not
link/reference the customer-upload's own Storage objects. A newly promoted design gets its own
`/originals/{designId}.png`, `/thumbnails/{designId}.webp`, `/previews/{designId}.webp`, copied
from the customer-upload's `productionStoragePath`/`previewStoragePath`/`thumbnailStoragePath`.
Per ADR-FP-086 §4, the customer-upload's own full-size copy is purged 14 days after `promotedAt`
via `purgePromotedDonationFullSize` — so there is a real, evidence-confirmed **temporary
duplication window** (both the customer-upload's originals and the catalog's copies exist
simultaneously for up to 14 days) that is a genuine, if bounded and already-intentional, Storage
cost. This Plan does not change that policy (it belongs to ADR-FP-086/Goal #11 territory) but the
Storage inventory (§Measurement below) must be able to identify and separately account for these
in-cool-off duplicates so they are never misclassified as orphans.

### 6. Whether one shared WebP derivative can safely replace both preview and thumbnail

**Feasibility: yes, from the generation-code evidence, with one required product decision.**
Preview (1280×1280 @ Q85) and thumbnail (320×320 @ Q80) are generated independently from the same
source bytes using the identical sharp pipeline (`fit: "inside"`, `withoutEnlargement: true`,
alpha-preserving WebP encode). There is no technical obstacle to generating one derivative at one
resolution/quality and using it for both grid and detail contexts — every consumer already treats
`thumbnailPath` as the safe universal fallback and `previewPath` as an optional "prefer bigger if
present" enhancement.

**The open product question this Plan does not resolve unilaterally:** at what single bounding box
does a shared derivative serve *both* a 320px grid cell acceptably *and* a detail-view/larger
preview acceptably? Sending a 1280px image into every 320px grid cell wastes bandwidth
proportional to the grid's row/page density (Portal Discover renders many cards per page); sending
a 320px image into a detail modal will look soft on higher-DPI displays. This is exactly the kind
of UI-rendering-size measurement the owner's brief explicitly says must not be skipped ("Do not
choose final dimensions or quality settings without evidence from current UI rendering sizes and
existing assets") — **this Plan recommends 640×640 @ Q82 as a starting hypothesis** (splits the
difference, matches common 2x-DPI-safe rendering for a ~320px grid cell, still usable at moderate
detail-view sizes) **but flags exact final dimensions/quality as a required Human Checkpoint**,
to be confirmed against actual measured Portal/Studio grid cell CSS dimensions and a visual sample
review before Implement finalizes it (see Human Checkpoints below).

### 7. Whether a separate tiny thumbnail is justified by measurement

No performance measurement of "shared derivative at grid size" vs. "dedicated 320px thumbnail" has
been run — there is nothing in the repository to measure against yet since the shared derivative
doesn't exist. Per the owner's explicit instruction ("Keep a separate tiny thumbnail only if
measured performance proves it is materially necessary... Do not preserve a thumbnail merely
because it already exists"), this Plan's default recommendation is **no separate thumbnail** —
one shared derivative — **unless Implement's own controlled-sample measurement (staged migration
step 1-2, below) shows a material regression** in initial catalog load, bandwidth, memory, Electron
rendering, or generated-manifest size. This is a decision Implement must produce evidence for, not
one this Plan can respond to speculatively.

### 8. Transparency and preview-background behavior

`DERIVATIVE_PRESERVE_ALPHA = true` is already respected by both existing derivatives via
`alphaQuality: options.quality` on the sharp WebP encoder (`encodeWebpDerivative.ts`). A single
shared derivative generated by the same encode call preserves this identically — no format change
(still WebP, still alpha-capable), so existing dark/light preview-background compositing logic
(wherever it reads `artworkBackgroundHex` and composites behind a transparent WebP) is unaffected
structurally. `artworkBackgroundHex` is already an optional field on the Portal catalog card
(`snapshotBuilders.ts:142-144`) independent of which derivative path is used.

### 9. Downstream pipelines requiring a separate format

No consumer requiring PNG, JPEG, or any non-WebP format for the *derivative* (as opposed to the
*original*) was found. Show Queue export/gang-sheet always uses the original PNG exclusively
(§4, confirmed). No email, Open Graph, or social-sharing consumer of `thumbnailPath`/`previewPath`
was found in this pass — Portal's own OG image composition (`portalOgImageCompose.ts`, from prior
Goal work) operates on customer-upload/brand-logo bytes directly, not catalog `thumbnailPath`.
**[NEEDS REPO CHECK — low confidence]:** whether any Portal social-share/OG surface embeds a
catalog design's thumbnail specifically; not confirmed absent, only not found in this pass's
consumer sweep. Implement should re-grep before assuming zero OG dependency.

### 10. Generated catalog manifest embedding

`mapPortalCatalogCard` (`snapshotBuilders.ts:110-160`) embeds `thumbnailPath` (required) and
`previewPath` (optional) as Storage **paths**, never download URLs, never embedded bytes. No
per-image content-hash/version field exists on the card itself — cache-busting for the actual
image *bytes* at a stable path is handled entirely client-side via `design.updatedAtMs` passed
into `getDownloadUrlForCatalogPath(path, updatedAtMs)`
(`catalogStorageService.ts:62-79,134-136`), which folds `updatedAtMs` into an in-memory
resolved-URL cache key — not a Storage/CDN-level cache-bust, a client-session-level one. The
manifest's own `contentVersion` mechanism (`snapshotBuilders.ts:35-38`, sha256-based) versions
taxonomy/manifest JSON content, not individual image bytes.

### 11. Existing cache invalidation dependency on filenames/content-versions

Confirmed: none of the three catalog object families have content-hash/version segments in their
paths (overwrite-in-place by `designId` only). Client-side freshness relies entirely on
`design.updatedAtMs` changing whenever the design doc is rewritten (which import/promotion/edit
flows already do via `serverTimestamp()`). **This means a migration that writes a new field (e.g.
`displayPath`) and bumps `updatedAt` will automatically invalidate every client's resolved-URL
cache for that design** — no new cache-invalidation mechanism needs to be invented.

### 12. Storage lifecycle rules

**[NEEDS REPO CHECK]** — Firebase Storage bucket lifecycle rules are a GCS bucket-level
configuration, not something expressed in `storage.rules` (which is access control, not
lifecycle/TTL). No lifecycle configuration file was found in this repository (no `gcs-lifecycle
.json` or equivalent). If any lifecycle rule exists, it was configured directly in the Google Cloud
Console, outside source control, and this Plan cannot confirm or deny its existence from
repository evidence alone. Implement must not assume none exists; the Storage inventory tool
(below) should report object `timeCreated`/`updated` metadata precisely so any silent
lifecycle-driven deletion would be visible as an unexpected object-count delta between inventory
runs, not investigated further in this Plan/Review phase.

### 13. Abandoned/temporary/failed-processing objects

Confirmed via `promoteCustomerUploadToAiReview.ts:230` (`if (promoteResult.copyAssets ||
!originalExists)`): a promotion retry re-copies objects if the original doesn't yet exist,
suggesting a possible partial-copy failure mode is already defensively handled by re-attempting
the copy — this is evidence *against* orphaned partial-promotion objects being a live problem, not
evidence for it. Import reprocessing/retry (`importDerivativeService.ts` rollback/retry logic, per
research) can, on failure-then-retry, call `uploadBytes` twice at the same deterministic path —
this **overwrites**, not duplicates (same path), so it is not a Storage-growth source, only a
"most recent write wins" data-integrity consideration already inherent to the existing
architecture and unrelated to this Plan's scope.

### 14. Duplicate derivatives from retry/reprocessing

Per §2/§13: each import mints a **new** `designId`
(`designService.generateDesignId()`, confirmed call site in `importOrchestrationService.ts:140`)
with no duplicate-detection/content-addressing check against existing designs — so **re-importing
the same source PNG twice creates two full sets of Storage objects** (this is a genuine,
already-existing behavior, not introduced by this Plan, and out of this Plan's scope to fix — flagged
here only because the Storage inventory tool must be able to surface these as "suspected
duplicate content, different designId" candidates for owner awareness, not silently resolve them).

## Storage Measurement / Inventory Method

**No deletion occurs in this phase.** The Plan defines a reproducible, repository-supported
inventory approach for Implement to build (not build now):

### Design

A new owner-only, dry-run-only `onCall` callable — `inventoryCatalogImageStorage` — modeled
directly on the confirmed `purgeIdleCustomerUploadFullSize.ts` dry-run precedent (bounded scan,
itemized JSON result, no manifest file needed since the callable response *is* the manifest):

1. Paginated `bucket.getFiles({ prefix: "originals/" })` /`"thumbnails/"` / `"previews/"` (the
   same `bucket.getFiles({ prefix })` pattern already used in `wipeOperationalTestData.ts:311-367`
   for prefix-scoped enumeration) — bounded batch size per invocation, resumable via a
   page-token/cursor response field (mirroring `purgeIdleCustomerUploadFullSize`'s `SCAN_LIMIT`
   pattern) so a full-bucket scan never risks a single-invocation timeout.
2. For every object found: read `name`, `size`, `timeCreated`, `updated`, `contentType` from GCS
   metadata (no download of bytes required — metadata-only listing).
3. Cross-reference against a bounded batch of `designs` collection reads (`designId` extracted from
   filename) to classify each object as:
   - **Referenced** — a `designs/{designId}` doc exists and its `originalPath`/`thumbnailPath`/
     `previewPath` field matches this exact object path.
   - **Orphaned candidate** — no matching `designs` doc exists, or the doc exists but its path
     field points elsewhere (stale/replaced reference).
   - **Purged-per-policy** — the `designs` doc exists, is `archived`, and has `assetsPurgedAt` set
     (ADR-FP-084) — an object that legitimately should no longer exist; if it does, that's a
     **`purgeArchivedDesignAssets` bug signal**, not routine orphan cleanup, and must be flagged
     distinctly.
   - **Promotion-cool-off duplicate** — cross-referenced against `customerUploads` docs with a
     matching `promotedDesignId` and `promotedAt` within the 14-day window (ADR-FP-086 §4) — a
     known, policy-sanctioned temporary duplicate, never flagged as deletable.
4. Aggregate and report: object count and total/average bytes **by path family**
   (`originals`/`thumbnails`/`previews`), referenced vs. orphaned-candidate totals, promotion-cool-off
   duplicate totals, and (cross-referencing `designs` docs with no matching Storage object) any
   **Firestore-references-missing-object** cases — a distinct, higher-severity signal (a design
   whose image is simply gone) that this tool must also surface, not just the reverse direction.
5. Dry-run only in this phase and for the tool's initial implementation — no delete path is built
   until a separate, later, owner-approved cleanup phase (see Orphan and Duplicate Handling below).

### Why this is reproducible and repository-supported (not "trust Firebase Console")

The Firebase Console's aggregate byte totals cannot distinguish `originals` from `previews` from
`thumbnails`, cannot cross-reference Firestore, and cannot identify promotion-cool-off duplicates
vs. genuine orphans. This callable-based inventory is deterministic, re-runnable, diffable across
two points in time (to detect unexpected growth or unexpected deletion), and produces a
structured, owner-reviewable report — matching the exact bar the owner's brief sets.

## Target Architecture Evaluation

### Original production asset — unchanged

`/originals/{designId}.png` remains exactly as-is: staff-only Storage Rules access, used
exclusively by Show Queue export/gang-sheet generation (confirmed, §4), never substituted by any
derivative. **No change proposed to this object family at all.**

### Shared display derivative — recommended, pending dimension/quality Human Checkpoint

Recommendation: introduce **one** new WebP derivative, generated by the identical existing sharp
pipeline (`fit: "inside"`, `withoutEnlargement: true`, alpha-preserving), at a bounding box and
quality to be confirmed by Implement's controlled-sample + UI-measurement step (§6 above;
**starting hypothesis 640×640 @ Q82**, not final). Reuses the same content-type/validation pattern
already enforced by `storage.rules` (`isValidDerivativeUpload()`).

**New deterministic path** (additive, not replacing the old ones during migration):
`getDisplayStoragePath(designId) -> /display/{designId}.webp` — a new top-level prefix, not nested
under `previews/`/`thumbnails/`, so old and new Storage Rules match-blocks can coexist without
regex ambiguity during the staged migration.

### Optional tiny thumbnail — deferred to measured evidence

Per §7: default to none; only add back if Implement's own measurement proves a material
regression. If added, it would be a genuinely tiny (e.g. ≤150×150) derivative reserved for the
highest-density grid contexts only, generated from the same source in the same encode pass (near-
zero marginal cost since generation already happens in one `sharp` pipeline invocation per
design).

## Required Technical Analysis

1. **Recommended format:** WebP (unchanged from today — already alpha-capable, already the
   established convention, no format migration risk).
2. **Width/height strategy:** maximum bounding box (`fit: "inside"`), matching the existing
   pattern exactly — not a fixed crop, not a fixed aspect ratio.
3. **Bounding box vs. fixed size:** bounding box, confirmed correct by existing consumer code (all
   consumers already render into flexible containers, not fixed pixel `<img>` tags, based on the
   `fit: "inside"` pattern already used) — final numeric value is the Human Checkpoint in §6.
4. **Generated from original or an intermediate:** from the original PNG source bytes directly (the
   same `productionPng`/`inputBuffer` both existing derivatives already use) — never chained
   through an existing derivative, to avoid compounding compression artifacts.
5. **Transparency:** preserved identically (`alphaQuality` on the WebP encoder, unchanged
   mechanism).
6. **Compression/quality:** starting hypothesis Q82 (between today's Q80 thumbnail and Q85
   preview); final value confirmed by visual-quality review (Human Checkpoint).
7. **Expected average byte reduction:** cannot be quantified without the Storage Measurement tool's
   real output against real catalog assets — **[NEEDS MEASUREMENT]**, not invented here. Directionally:
   replacing two objects with one at an intermediate size is expected to reduce *object count* by
   33% (3→2 per design) unconditionally, and reduce *combined preview+thumbnail bytes* by an amount
   dependent on real image content (WebP byte size scales sub-linearly with pixel count for typical
   catalog art, so a 640×640 single derivative is very unlikely to cost as much as today's
   320×320+1280×1280 combined, but the exact percentage requires measurement).
8. **Expected Storage reduction per design:** one fewer permanent object per design (thumbnail and
   preview become one `display` object) once migration completes and old objects are deleted in a
   later, separately-approved phase — no reduction during the Plan/Review/Implement phases
   themselves, since old objects are explicitly retained until proven safe to remove.
9. **Expected Portal bandwidth reduction:** grid contexts that currently load 320×320 continue to
   load approximately the same or modestly more bytes (640×640 is larger than 320×320); detail
   contexts that currently load 1280×1280 load meaningfully fewer bytes (640×640 vs 1280×1280). Net
   direction depends on the real grid-vs-detail traffic mix — **[NEEDS MEASUREMENT]**, flagged
   explicitly rather than asserted.
10. **One derivative for both grids and previews:** yes, per §6-7 — this is the core recommendation,
    conditional on the dimension/quality Human Checkpoint.
11. **Cache-Control headers:** **new gap to close** — today's derivatives set none (§3). The new
    `display` derivative should set an explicit `Cache-Control` (e.g. matching the customer-upload
    convention, `"public, max-age=<N>"` since these are public-readable ready-design assets, not
    `"private"` like customer uploads) — this is a genuine improvement opportunity uncovered by
    this investigation, not a regression risk, since today's objects have no header at all.
12. **`contentType` metadata:** `image/webp`, unchanged pattern (`DERIVATIVE_WEBP_CONTENT_TYPE`).
13. **Deterministic paths:** `/display/{designId}.webp`, mirroring the existing `designId`-keyed,
    overwrite-in-place convention exactly (no new architectural pattern introduced).
14. **Overwrite vs. versioned-object strategy:** overwrite-in-place, matching existing
    `originals`/`thumbnails`/`previews` convention — versioning is unnecessary given §11's finding
    that `updatedAtMs`-keyed client-side cache invalidation already exists and requires no new
    mechanism.
15. **Cache-busting/rollback:** existing `design.updatedAtMs` → `getDownloadUrlForCatalogPath`
    cache-key mechanism (§10-11) is reused as-is; no new cache-busting mechanism required.
16. **Interaction with generated manifests/content versions:** adding an optional `displayPath`
    field to `mapPortalCatalogCard` (additive, not replacing `thumbnailPath`/`previewPath` yet) will
    automatically flow into the manifest's existing `contentVersion` hash the next time a
    publish/rebuild runs (since `contentVersion` hashes the full card object) — no special-case
    propagation logic needs to be built.
17. **Old fields remain during migration:** yes — `thumbnailPath`/`previewPath` remain untouched and
    fully functional throughout Implement and the staged migration; `displayPath` is purely
    additive.
18. **Firestore schema changes required:** yes, additive-only — new optional `displayPath?: string`
    field on `designs` docs (and the `PortalCatalogCard`/generated-manifest shape, additive/optional
    there too). **This is a schema change and is a Human Checkpoint** per the owner's brief.
19. **Dual-read/fallback period required:** yes — every consumer already has a
    `previewPath ?? thumbnailPath` fallback pattern; the migration extends this to
    `displayPath ?? previewPath ?? thumbnailPath` (detail contexts) and `displayPath ??
    thumbnailPath` (grid contexts), so a design that hasn't been backfilled yet degrades gracefully
    to its existing derivatives — never a broken image.
20. **Storage Rules changes required:** yes — a new `match /display/{fileName}` block, structurally
    identical to the existing `/thumbnails/`/`/previews/` blocks (same `isCanonicalDerivativeFileName`-style
    regex adapted to the new prefix, same `isValidDerivativeUpload()`, same
    `isReadyDesignDerivative()`-style public-read gate). **This is a Storage Rules change and is a
    Human Checkpoint.**

## Original-Production Protection Strategy

- `/originals/{designId}.png` is never read, written, or deleted by any code this Plan proposes.
- Show Queue export and gang-sheet generation continue to resolve `design.originalPath` exclusively
  (§4) — no code path in this Plan touches `useExportShowZip.ts` or `useExportGangSheetPng.ts`.
- The new `display` derivative is generated from the original's decoded bytes but never
  substitutes for the original in any production/export/print context — enforced structurally by
  giving it an entirely separate field name (`displayPath`) that no export code will be modified to
  read.

## Migration and Rollback Strategy (staged, non-destructive)

1. Implement the `display` derivative generator (reusing the existing shared sharp/WebP encode
   pipeline) and a controlled-sample backfill limited to a small owner-chosen set of designs.
2. Owner visually reviews the sample: transparency, quality, dimensions, and real measured byte
   savings vs. the existing preview+thumbnail pair for those same designs. **Human Checkpoint.**
3. Add `displayPath` (optional) to `designs` Firestore schema and to the generated
   `PortalCatalogCard` shape — additive only; `thumbnailPath`/`previewPath` untouched.
   **Human Checkpoint (schema change).**
4. Migrate consumers one group at a time (e.g. Portal grid cards first, then Portal detail modals,
   then Studio grid cards, then Studio detail views), each consumer falling back to
   `thumbnailPath`/`previewPath` when `displayPath` is absent — never a hard cutover.
5. Bounded-concurrency backfill for the remaining catalog (~80 designs today — small enough that
   even a conservative concurrency-3 bound, matching the established `boundedConcurrencyQueue.ts`
   precedent from Goal #9, completes quickly) generating `displayPath` for every existing `ready`
   (and, separately considered, `archived`-but-not-yet-purged) design.
6. Verify: every `designs` doc with `displayPath` set has a corresponding Storage object; every
   Storage `/display/{id}.webp` object has a corresponding `designs` doc reference (bidirectional
   consistency check, reusing the inventory tool's cross-reference logic from the Measurement
   section).
7. Confirm every consumer group has switched (grid cards read `displayPath ?? thumbnailPath`,
   detail views read `displayPath ?? previewPath ?? thumbnailPath`) via the regression tests below.
8. Re-run the Storage inventory tool; measure actual Storage/bandwidth improvement against the
   pre-migration baseline captured in step 1's controlled sample.
9. **Stop for owner approval before deleting any old `/thumbnails/`/`/previews/` object** — this
   Plan does not authorize deletion at any point; a future, separate goal (with its own Plan/Review)
   is required to actually remove the superseded objects, once rollback safety is proven over a
   owner-chosen observation window.
10. Rollback path: since `thumbnailPath`/`previewPath` are never removed or modified during this
    migration, rollback is simply reverting the consumer-side fallback order (or the `displayPath`
    field read) to its pre-migration state — no data loss possible, since nothing old was ever
    deleted.

## Orphan and Duplicate Handling

Per the Storage Measurement Method's classification (Referenced / Orphaned candidate /
Purged-per-policy / Promotion-cool-off duplicate), plus:

- **Confirmed unreferenced:** an object whose `designId` has no matching `designs` doc at all
  (design fully deleted from Firestore but Storage object survived) — highest-confidence deletion
  candidate, but still requires the dry-run manifest + owner checkpoint before any actual delete.
- **Retry artifact:** cannot be distinguished from a normal object by path alone (overwrite-in-place
  means a retried upload has the identical path as the original attempt) — this is a structural
  property of the existing architecture, not something the inventory tool can detect after the
  fact; noted as a known limitation, not solved by this Plan.
- **Duplicate content, different designId:** the two-full-object-sets-from-re-import scenario (§14)
  — detectable only by content-hash comparison across `originals/`, which this Plan's inventory
  tool does not attempt in its first version (out of scope; flagged as a possible v2 enhancement,
  not blocking this Plan).
- **Archived-design asset:** `designs` doc `status == "archived"` with no `assetsPurgedAt` — original
  and previews are still legitimately present and must never be flagged as deletable regardless of
  age.
- **Failed-processing artifact:** **[NEEDS REPO CHECK]** — no evidence found of a distinct
  "failed/partial" object state for catalog images (unlike customer-uploads' `technicalStatus:
  failed`); Implement should re-verify this absence before finalizing the classification schema.

**Any cleanup tool defaults to dry-run** (mirroring `purgeIdleCustomerUploadFullSize.ts`'s exact
`dryRun` request-shape convention) and produces an owner-reviewable manifest containing: Storage
path, byte size, creation time, related Firestore entity (if any), reason it appears deletable,
confidence level, and proposed action. **No deletion occurs without a separate owner checkpoint** —
this applies to the inventory tool itself (dry-run only in this Plan's scope) and to any future
actual-delete tool (a separate, later goal).

## Interaction with Archive-Purge (Formal Review Required Change 1)

`purgeArchivedDesignAssets.ts:41-56` (`deleteLargeDesignAssets`) deletes only
`getOriginalStoragePath`/`getPreviewStoragePath` and has no knowledge of `displayPath` — this Plan
does not modify that callable. **Named consequence, not an oversight:** once `displayPath` exists
on any design, an owner purging that design's images via the existing archive-purge flow will
delete `originals`+`previews` and keep `thumbnails` exactly as today, but the design's
`displayPath` Storage object will be **silently orphaned** (neither deleted nor retained with
intent) — it simply becomes an object the purge callable doesn't know to touch. This is a real,
near-term transitional gap the moment `displayPath` exists in production data, not a hypothetical.
It is explicitly deferred to a future goal (reconciling `purgeArchivedDesignAssets`'s retention
policy with the new field) rather than resolved here, and Implement must be aware of it before
backfilling any design that could plausibly be archived and purged during the transitional period.

## Cache-Control Transitional Inconsistency (Formal Review Required Change 3)

Setting an explicit `Cache-Control` header on new `display` objects (Technical Analysis item 11)
while today's `thumbnails`/`previews` objects remain header-less creates an intentional,
**accepted** inconsistency during the migration window: a design that has been backfilled serves a
cache-header-bearing `display` object, while a design not yet backfilled continues serving
header-less `thumbnails`/`previews` exactly as today. This is not an oversight — it resolves itself
automatically once migration completes and is not worth blocking on, but is stated explicitly here
so it is never mistaken for a regression during Implement or Test.

## Storage Inventory Classification Test Seam (Formal Review Required Change 2)

The Storage inventory's classification logic (referenced / orphaned candidate / purged-per-policy /
promotion-cool-off duplicate) must be extracted as a **pure function operating on already-fetched
metadata arrays** (object listings + a bounded batch of `designs`/`customerUploads` doc data passed
in as plain objects), directly unit-testable with synthetic fixtures — no Storage/Firestore
emulator required. This follows the same extraction pattern already proven three times in this
codebase (`withTimeout.ts`, `withCustomerUploadFinalizeWatchdog.ts`,
`evaluateCustomerUploadFullSizeRetention`): keep the `onCall` shell (actual `bucket.getFiles()`/
Firestore reads) thin, and put every classification decision in a pure function the `onCall` shell
calls. Only the thin I/O shell itself is expected to need any live-service testing, and per this
repository's confirmed absence of a live-callable integration-test harness (established across
Goals #10 and #11), that shell is not expected to get a dedicated automated test — its correctness
is covered by the pure function's tests plus manual owner verification of a real dry-run output.

## Rollback Plan

No deployment or migration occurs in this Plan/Review phase. Once a future Implement phase runs:
rollback is reverting consumer fallback-chain code and/or the `displayPath` field read — no data
loss is possible because `thumbnailPath`/`previewPath` and their underlying Storage objects are
never modified or deleted by this Plan's design. A full architectural rollback (removing
`/display/` entirely) would require deleting the new Storage objects and the new Firestore field —
itself subject to the same dry-run-first, owner-approved deletion discipline as any other cleanup.
