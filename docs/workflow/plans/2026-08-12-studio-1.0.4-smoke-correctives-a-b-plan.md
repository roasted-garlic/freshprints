## Proven findings (repo inspection)

### Starting SHA

`origin/production` = **`4ac77141f0f12845e1ca11b742c5242488496b70`** (contains PR #65 + #66).

### Defect A — current path

1. `ImportsPage` / batch UI → renderer import services  
2. Preload `window.freshPrints.imports` → IPC  
3. Main **`validatePngFile`** (`apps/studio/electron/ipc/import/pngValidator.ts`) — used by single validate + folder/multi/zip discovery  
4. On pass: read bytes → Storage upload → `designService.createDesign` → derivatives → AI enqueue  

**Exact reason opaque artwork currently passes:**  
There is **no** meaningful-transparency / alpha-pixel gate anywhere in the Studio import pipeline. Existing gates are extension, size, PNG parse (dims/DPI only — **not** color-type/alpha policy), transparent-edge **trim** (corrective, not reject), print-size, upscale. Opaque PNGs validate, upload, create designs, and can enqueue AI.

### Existing transparency validator

| Piece | Location |
|-------|----------|
| Pure predicate + thresholds | `packages/shared/src/utils/customerUploadTransparency.ts` → `assessMeaningfulTransparency` |
| Sharp sample + trim probe | `functions/src/lib/customerUploadProcessing.ts` (private helpers) |
| Policy | α **&lt; 250**; pass if transparent ratio **≥ 0.5%** OR trim shrink either axis **≥ 1%**; fail closed on measurement failure |

**Reuse strategy (required):**  
Reuse **`assessMeaningfulTransparency` + existing constants** — do **not** invent a second threshold. Extract sharp decode/sample/trim-probe measurement into a shared Node helper (Sharp factory injected) used by Functions + Studio Electron so Portal does not gain a `sharp` dependency. Studio staff-facing rejection message must clearly state catalog artwork requires a transparent background (wording may differ from Portal’s “Background is not transparent.” without changing pass/fail math).

**Partial / noisy-alpha ambiguity:**  
Not a new product decision in this phase — Studio adopts the **already-shipped** customer-upload meaningful-transparency policy for catalog imports. Fully opaque fails; genuine transparent passes; edge padding/trim remains after a pass. No Studio-only soft threshold. Hard reject for Studio catalog import (**no** `skipQualityGates` bypass on this path).

### Defect B — UI → service → Rules

1. `AiReviewWorkspace` Archive → `AiReviewPage` → `useAiReviewInbox.archiveSelected`  
2. `canArchiveDesigns(user)` = `isStaff` (UI enables Archive for staff)  
3. `aiReviewInboxService.archiveFromInbox` → `catalogApprovalService.archiveRejectedDesign` → **`designService.archiveDesign`**  
4. Payload: `status: "archived"`, `previousStatus`, `archivedAt`, `archivedBy`, `updatedAt`, `updatedBy`  
5. Firestore `designs/{id}` `allow update`

**Observed error string** `"You do not have permission to perform this action."` maps from Firestore **`permission-denied`** via `firestoreErrorMessage.ts` — **not** the client role message (`"You do not have permission to archive designs."`).

**Proven Rules gap:**  
Archive keys are **absent** from `catalogApprovalStatusOnlyUpdate()` allowlist. Companion/metadata fast paths require status unchanged. Archive therefore falls through to full **`designRequiredFieldsValid`** after still paying the approval-path `diff()` — same expression-budget failure class already documented for enrichment-heavy catalog approval. Admin auto-archive bypasses Rules (Admin SDK).

**Root cause (best-supported):** missing archive fast path → enrichment-heavy rejected designs deny on expression budget / full validator path. Field-type mismatch is refuted (archive fields already optional in full validator). Client permission mismatch is refuted by error string + enabled Archive button.

**Rules must change:** **Yes** — client soft-archive cannot be fixed in renderer alone.

## Approach

### Branching

1. Verify `origin/production` still `4ac77141…` before branch.  
2. Branch e.g. `hotfix/studio-1.0.4-smoke-correctives-a-b` from that tip.  
3. No direct-push to production. Production promotion via **CHATGPT GITHUB HANDOFF**.

### Defect A implementation order

1. Extract/reuse measurement: sharp sample (max side 800) + trim-shrink probe → `assessMeaningfulTransparency`.  
2. Detect alpha via sharp/source metadata (`hasAlpha`), **not** extension / color-type alone.  
3. In `validatePngFile`, run transparency check on **source file bytes** before treating the file as valid for upload (preserve existing trim/upscale/print-size order for files that pass transparency — do not regress trimming).  
4. Throw `PngValidationError` with staff-clear message: catalog artwork requires a transparent background.  
5. Map batch rejection reason `BACKGROUND_NOT_TRANSPARENT` (or equivalent) so folder/ZIP/multi share the same gate (all call `validatePngFile`).  
6. Fixture tests: fully opaque PNG reject; true transparent PNG pass; confirm no Storage/design/AI on reject (unit/orchestration-level assertions as feasible; main-process validation is the hard gate).

### Defect B implementation order

1. Add emulator tests that **reproduce deny** for enrichment-heavy `rejected → archived` under current Rules (prove root cause).  
2. Implement narrow `designArchiveStatusOnlyUpdate()`:
   - `resource.data.status != "archived"`
   - `request.resource.data.status == "archived"`
   - `diff().affectedKeys().hasOnly(["status","previousStatus","archivedAt","archivedBy","updatedAt","updatedBy"])`
   - identity fields unchanged (`id`, `uploadedBy`, `createdBy`/`createdAt` if present)
   - `previousStatus == resource.data.status`
   - `archivedBy == request.auth.uid`, `updatedBy == request.auth.uid`
   - timestamps valid
   - staff via existing `isStaff()` on `allow update`
   - no AI / purge field changes (implicit via hasOnly)
3. Place fast path in `allow update` OR-chain so archive does not fall through to full validator; optionally make `catalogApprovalStatusOnlyUpdate` fail cheap when requested status is `archived`.  
4. Emulator: ALLOW rejected(+large AI)/ready archive; DENY forged AI fields, wrong `previousStatus`, non-staff, extra keys.  
5. Preserve restore authorization unchanged.  
6. Confirm AI Review list/count behavior still drops archived designs (existing eligibility — regression check).

### DEV → production sequence

1. Localhost: Studio typecheck/lint + focused tests + Rules emulator.  
2. Human checkpoint: deploy **reviewed Rules only** to `fresh-prints-dev`.  
3. Owner DEV QA: opaque/transparent import; archive rejected design as owner + helper.  
4. CHATGPT handoff: PR merge to production (Studio + Rules as one or coordinated PRs).  
5. Separate auth: production Rules deploy.  
6. Separate auth: stable dual-platform draft rebuild from **new** tip (do not reuse `369535832`).  
7. Re-smoke (Mac + then Intel/Windows as owner directs).  
8. Separate auth: publish.
