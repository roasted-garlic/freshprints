## Goal

Investigate why published Studio **1.0.9** (GitHub release **375869566**) retained tag `untagged-ac82c9de5862b0ae7d2d` instead of `v1.0.9`, then — after Formal Review and explicit owner authorization — safely retag the **existing** published release in place without rebuilding, republishing assets, or mutating **v1.0.8**. Add a preventative release-process fix so **1.0.10+** cannot repeat this gap.

## Background

Parent goal `production-promote-portal-and-studio-2026-08-23` published Studio 1.0.9 successfully (Latest, updater metadata, smoke PASS). Signoff noted the non-standard tag as **approved_with_notes**. Owner now wants hygiene correction and workflow hardening.

Prior precedent:

- **1.0.8** draft + publish used tag **`v1.0.8`** end-to-end (`374575547`).
- **1.0.4** collision era used suffix tag **`v1.0.4-e59205d`** when `v1.0.4` was in use; GitHub also auto-assigns `untagged-*` slugs when multiple drafts claim the same semantic tag (documented in `2026-08-12-studio-1.0.4-dual-platform-draft-verification.md`).
- **2026-08-21** publish helper added Latest + final copy but **does not set `tag_name`**.

## Root cause (investigation complete)

### 1. Where `untagged-ac82c9de5862b0ae7d2d` was created

| Layer | Location | Evidence |
|-------|----------|----------|
| Draft create | `.github/workflows/studio-release.yml` → `finalize-release` → bash block ~L630–657 | `gh api --method POST …/releases` with `-f tag_name="$CREATE_TAG"` |
| Workflow run | [32754684436](https://github.com/roasted-garlic/freshprints/actions/runs/32754684436) finalize log | `FINALIZE_OK release_id=375869566 tag=untagged-ac82c9de5862b0ae7d2d sha=f35c96d… draft=true` |
| Git ref | `refs/tags/untagged-ac82c9de5862b0ae7d2d` → commit `f35c96dda23ce83f99f75ab3f942c5edfcfcfdd2` | `gh api …/git/ref/tags/untagged-ac82c9de5862b0ae7d2d` (lightweight tag) |

No other repo script creates GitHub release tags. Publish helper does not create tags.

### 2. Why `v1.0.9` was not used

| Check | Result |
|-------|--------|
| Remote git tag `v1.0.9` | **Absent** (`git ls-remote --tags origin`) |
| Any release with `tag_name` matching `v1.0.9` / `1.0.9` | **0** (paginated API) |
| Workflow `TAG_IN_USE` warning in run 32754684436 | **Absent** — workflow believed `v1.0.9` was free and POSTed `CREATE_TAG=v1.0.9` |
| API `tag_name` after POST | **`untagged-ac82c9de5862b0ae7d2d`** — GitHub-assigned slug (same class as 1.0.4 draft collision docs) |

**Conclusion:** Not owner intent. The workflow requested `v1.0.9`, but GitHub persisted an auto `untagged-*` tag. The workflow’s collision fallback (`v1.0.9-f35c96d`) did **not** run because `TAG_IN_USE` queries only exact `tag_name == "v1.0.9"` and found nothing.

### 3. Intentional collision avoidance vs bug vs process gap

| Category | Assessment |
|----------|------------|
| Intentional | **No** — owner expected normal `v1.0.9` URL parity with 1.0.8 |
| Workflow bug (finalize) | **Partial** — collision detection is incomplete vs GitHub `untagged-*` behavior |
| Process gap (publish) | **Yes** — `publish-studio-stable-github-release.mjs` never sets `tag_name` to `v{version}` and never verifies tag shape after publish |

### 4. Publish step preserved the draft tag

`buildPublishPatch()` in `.github/scripts/studio-github-release-copy.mjs` sets only:

- `draft: false`
- `make_latest: "true"`
- `prerelease: false`
- `body: finalBody(...)`

It **omits `tag_name`**. Publish therefore left `untagged-ac82c9de5862b0ae7d2d` unchanged. This matches 2026-08-21 plan scope (“Do not rename assets or change binaries”) but created a hygiene debt when finalize did not yield `v1.0.9`.

### 5. Anomaly note (non-blocking)

Release `created_at` (`2026-08-24T16:31:17Z`) predates authorized workflow dispatch (`2026-08-24T17:06:15Z`). Only one Studio release run exists that day. Finalize attached assets to release **375869566** in that run. **Recommend owner GitHub audit log** if provenance of the 16:31 timestamp matters; it does not block in-place retag because `target_commitish` and assets match the authorized build.

## Proposed mutation sequence (DO NOT EXECUTE until authorized)

### Preflight (read-only)

1. `gh api repos/roasted-garlic/freshprints/releases/375869566` — confirm `draft=false`, `target_commitish=f35c96d…`, **8 assets**
2. `gh api repos/roasted-garlic/freshprints/releases/latest` — confirm id **375869566**
3. `git ls-remote --tags origin` — confirm **`v1.0.9` absent**
4. `gh api repos/roasted-garlic/freshprints/releases/374575547` — confirm **v1.0.8 unchanged**
5. Download `latest.yml` — record `version: 1.0.9`, relative `path` (no tag-specific URLs)

### Mutation (owner checkpoint — destructive Git/tag)

6. **PATCH release by ID** (preferred over raw tag delete):

```bash
gh api --method PATCH repos/roasted-garlic/freshprints/releases/375869566 \
  --input - <<'EOF'
{
  "tag_name": "v1.0.9",
  "name": "1.0.9",
  "target_commitish": "f35c96dda23ce83f99f75ab3f942c5edfcfcfdd2",
  "draft": false,
  "prerelease": false,
  "make_latest": "true"
}
EOF
```

7. **Do not** PATCH `body` unless verification shows regression (final copy already applied).

### Post-mutation verification

8. `GET /releases/375869566` → `tag_name=v1.0.9`, asset count **8**, same asset names
9. `GET /releases/latest` → id **375869566**
10. `gh release view v1.0.9` → resolves to same release
11. Re-download `latest.yml` from **`v1.0.9`** tag — byte/compare or field check unchanged
12. `GET /releases/374575547` → **unchanged**
13. Optional: if `refs/tags/untagged-ac82c9de5862b0ae7d2d` still exists **and** is orphaned (no release points to it), delete ref via GitHub git API — **only after** step 8 confirms release uses `v1.0.9`. **Defer if uncertain.**

### Rollback / recovery

| Failure | Recovery |
|---------|----------|
| PATCH rejects (`422` tag exists) | **STOP** — investigate conflicting tag; do not delete v1.0.8 or 375869566 |
| Latest moves off 375869566 | PATCH again with `make_latest: "true"` on **375869566** only |
| `latest.yml` missing or changed | **STOP** — do not delete release; compare asset ids; escalate (should not happen on tag-only PATCH) |
| Wrong release retagged | **STOP** — owner checkpoint; PATCH back only if GitHub still allows |

Rollback to `untagged-ac82c9de5862b0ae7d2d` is possible via reverse PATCH **only if** `v1.0.9` ref can be moved safely — treat as last resort; record before/after API snapshots first.

## Preventative workflow fix (Phase 2 implement)

| Change | Rationale |
|--------|-----------|
| Extend `buildPublishPatch(version, sha)` to include `tag_name: "v${version}"` when `--expect-tag` or always for stable publish | Ensures publish step normalizes tag after draft finalize quirks |
| Extend `verifyPublishedRelease()` to assert `published.tag_name === \`v${expectedVersion}\`` (or allow documented suffix only with explicit flag) | Fail closed before signoff |
| Finalize: if POST returns `tag_name` starting with `untagged-`, emit **`::error::`** or auto-retry with `v${VERSION}-${SHORT_SHA}` | Prevents silent acceptance; aligns with 1.0.4 suffix precedent |
| Finalize: broaden `TAG_IN_USE` to include releases with `name == VERSION` and non-matching tag | Catches GitHub slug collisions |
| `DEPLOYMENT.md` signoff checklist: record **`tag_name=vX.Y.Z`** and `/releases/tag/vX.Y.Z` resolves | Operator visibility |
