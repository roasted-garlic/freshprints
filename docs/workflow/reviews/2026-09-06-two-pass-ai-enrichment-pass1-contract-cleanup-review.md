## Decision summary

The corrective is narrow and mechanically supported. The current request is rejected by Google because its schema has too many serving constraint states, and the active contract still carries obsolete tag and AI-halftone output. The proposed v39 contract removes those fields, removes provider-side `maxItems`, restores the owner-approved visual-analysis prompt, keeps dynamic approved-category descriptions, and preserves deterministic application behavior.

Implementation remains gated on owner-run direct HTTP validation of the fully cleaned artifact. The no-`maxItems` and cleaned request artifacts are ready; no result is claimed for either.

## Required formal answers

### 1. Why did obsolete tag fields survive?

They survived as historical compatibility residue from the earlier tag-matching architecture. The current candidate core already forces new-run tags to empty/skipped and retains a commented legacy resolver block, but the provider schema, parser, types, prompt inputs, and tests still describe the old contract. The corrective removes the active provider contract rather than relying on empty values.

### 2. Can active Tag AI fields be removed now?

**YES.** The current active path does not need provider tags to produce the current Smart Profile, category, title/description, VCP, or deterministic decisions. Historical `design.tags` remains readable/compatible outside the provider contract. Tag Rerank and Suggestion Author remain inactive and are not restored.

### 3. Which historical tag fields remain for compatibility?

Historical `design.tags` and any persisted historical AI suggestion fields may remain inert/readable. They are not requested from Gemini, not generated by Pass 1, not used as category influence, and not migrated or destructively deleted in this corrective.

### 4. Is `preferredWhen` absent from the proposed active enrichment path?

**YES.** It is removed from the Pass 1 schema, prompt, parser expectation, provider input, and active Pass 1 output. Catalog tag service/storage compatibility remains outside this provider contract.

### 5. Which AI-halftone fields/consumers retire?

Retire `halftoneShadowLikelihood` and `halftoneShadowEvidence` from the active schema, parser, canonical output, `DesignAiAnalysis` transient AI path, Smart Profile enrichment parse, Smart Profile builder shadow parser, Playground output filtering, telemetry/trace projections if only used for these fields, and their contract tests. Preserve `halftoneStaffDecision`, `halftoneDecisionSource`, intake/manual metadata, background workflow, and staff authority.

### 6. Is manual/intake halftone behavior unchanged?

**YES.** Manual/intake fields and their existing import, customer-upload, reprocess, Studio, and persistence paths are explicitly out of scope for removal.

### 7. Does the current prompt contain a hardcoded category snapshot?

The current code-owned v38 template contains the dynamic `{{approved_categories}}` placeholder, but recognized older Settings copies and expanded persisted/diagnostic prompt bodies can contain category text. The implementation will recognize current v38 as a previous stock prompt and resolve it to the v39 template. The v39 template contains no category snapshot.

### 8. What existing runtime path expands the placeholder?

`loadAiCatalogReferenceSnapshot` → `loadCachedActiveCategories` → `buildSimpleCatalogEnrichmentUserPrompt`. Both `aiEnrichmentPlayground.ts` and the Processing candidate path use this shared prompt expansion boundary.

### 9. How are categories formatted?

The existing formatter emits active entries as `- Category Name — Owner-written description`, with `(none)` if empty. No replacement taxonomy service is proposed.

### 10. Does Playground use the same category expansion as Processing?

**YES.** Both call `buildSimpleCatalogEnrichmentUserPrompt`; the parity tests will assert identical expansion for identical category/settings inputs.

### 11. How is stale Settings text reconciled?

Add the exact v38 body to the recognized previous-default set. `resolveAiEnrichmentPromptTemplate` remains read-only and returns v39 for recognized stock v38 (and older recognized stocks), while genuine custom prompts remain unchanged. No silent Firestore write is required. Studio Settings should display the resolved v39 stock default and preserve an actual custom prompt.

### 12. What exact prompt will ship?

The exact target is included in the Plan under “Proposed Pass 1 prompt.” It is the owner-supplied visual-analysis prompt with dynamic approved categories, no tags, no halftone detection, no giant JSON example, and no deterministic policy prose.

### 13. Is it materially simpler?

**YES.** It removes the literal output JSON example, tag-generation instructions, excluded-tag vocabulary, halftone detection, and historical policy prose while retaining visual description, meaningful text, semantic dimensions, category reasoning, search concepts, uncertainty, and VCP instructions.

### 14. Does it retain the successful cucumber-test behavior?

**YES.** It explicitly prioritizes visible artwork, accurate title/description, readable text, subjects, objects, styles, themes, colors, search concepts, buyer-intent category, and uncertainty. It does not restore obsolete experiment fields such as `suggestedCategory` or `explicitArtworkTerms`.

### 15. Is `visibleText` canonical?

**YES.** It is the current canonical top-level meaningful artwork-text field consumed by persistence, automation, and Explicit Content evidence.

### 16. Can `readableTextLines` be retired?

**YES for the active provider contract.** It is a historical/redundant provider field. If old fixtures require compatibility, the parser may accept it only as a bounded legacy alias and derive `visibleText`; no active prompt/schema/provider output will request or emit it.

### 17. Which other duplicates remain?

Top-level Smart Profile dimensions versus VCP dimensions (`objects`, `colors`, `professionsGroups`, `occasions`) are intentionally retained as distinct representations: retrieval/profile lists versus richer visual evidence. VCP `readableArtworkText` remains distinct evidence context; top-level `visibleText` remains canonical search/copy text.

### 18. How many provider `maxItems` remain?

**0.** All 27 current provider-side `maxItems` constraints are removed. Application-side caps remain.

### 19. Where are deterministic caps enforced?

`simpleCatalogEnrichmentResponse.ts` caps generic arrays, visible text, category alternatives, and VCP fields through existing normalizers and VCP constants. Implementation tests will exercise oversized arrays directly.
