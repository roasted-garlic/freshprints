## Why harness PASS vs packaged FAIL (narrow hypothesis — not implemented)

- `markDesignProcessing` (`imported→processing`, status-only) succeeds via Rules **`catalogApprovalStatusOnlyUpdate`** fast path (`hasOnly` status/AI/timestamp keys).
- `markDesignDerivativesComplete` (`processing→imported` **+** `thumbnailPath` **+** `previewPath`) **cannot** use that fast path → falls through to full `designRequiredFieldsValid` + `clientAiFieldsUnchanged`.
- That full-path update is what returns **permission-denied**.
- Prior DEV harness used a minimal `updateDoc` on thinner documents and passed; Studio `createDesign` writes a richer document, then `designService.updateDesign` for path persist — same project Rules, different write shape/cost.

**Recommended narrow corrective (do not implement in this stop):**

1. **Primary:** Add a Firestore Rules fast path (and/or slim update) for derivative-path completion: allow staff updates that only change `status` (`processing`→`imported`), `thumbnailPath`, `previewPath`, `updatedAt`, `updatedBy` (+ safe `createdBy` heal if already used elsewhere), without paying full `designRequiredFieldsValid` budget. Validate with Rules unit/emulator tests on rich import documents.
2. **Visibility:** Ensure batch Import results always show `derivativeError` when `pipelineSuccess=false`; AI Processing must not present derivative-failed imports as normal WAITING FOR AI without a failure badge.
3. **Diagnostics:** Preserve Firestore `permission-denied` code on wrapped Errors (as done for Storage `firebaseCode`).

Do **not** weaken Rules broadly. Do **not** blame Sharp/IPC/transparency.
