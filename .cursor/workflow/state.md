Gang sheet label font size setting, default width 23", DPI metadata fix, and rotation improvement (2026-07-06):
- User reported the same real bug independently surfaced during the trim-transparent-padding work: a real 8-image gang sheet export that should have come out ~23"x42.5" at 300 DPI instead reported as 273"x557.56" at 25 DPI in Photoshop, and asked to look at "the algorithm that tells images to rotate if it can save vertical space." Traced the actual pixel dimensions (6825x13939px) and confirmed two independent defects, both fixed here: (1) `exportGangSheetPng.ts` never called `sharp`'s `.withMetadata({ density })` on the composited PNG, so external tools reading embedded DPI got a wrong/default value even though pixel dimensions were already correct for 300 DPI internally; (2) `gangSheetNesting.ts`'s rotation logic only ever rotated a box that ended up completely alone in a row, never considering rotation for boxes sharing a row with others — exactly the case visible in the reported export (multiple portrait images stacked 2-per-row with no rotation attempted). Also added two small settings tweaks: a configurable gang sheet label font size (new `gangSheetLabelFontSizePx` setting, defaulted to 120px — double the previous hardcoded 60px, per feedback that the label was too small) and changed the default gang sheet width from 22.75" to 23". Wrote and got approval on `docs/workflow/plans/2026-07-06-gang-sheet-label-font-dpi-rotation-fix-plan.md`, with two scope decisions confirmed via AskUserQuestion: rotation stays a per-row greedy heuristic (try rotating a portrait box when it helps that row) rather than a full bin-packing rewrite, and no per-design "don't rotate" opt-out.
- Rotation algorithm redesign in `shared/utils/gangSheetNesting.ts` went through several iterations before landing on the correct rule, refined further after the user clarified mid-implementation: **any number of boxes sharing a row can rotate together, as long as their combined rotated width doesn't exceed the sheet's max width plus margins/gutters.** Final design: `resolveRowRotations` runs once per completed row, rotating any box tied for the row's tallest height (rotating a shorter box would only waste width for no benefit) whenever the rotated height is actually shorter and the *combined* row width — computed using other boxes' already-resolved (possibly-also-rotated) widths, via an in-place iterative resolution rather than a `.map()` snapshot, to avoid a race condition where two simultaneously-eligible boxes could each independently think there was room for both to rotate — still fits the usable width. A lone box in a row has no such fit constraint (nothing else to conflict with) and always rotates when portrait, preserving the original lone-box behavior exactly.
